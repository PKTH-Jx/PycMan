# PycMan：Python 程序设计基础大作业任务说明

## 作业目标

你将在吃豆人游戏框架上逐步完成移动、拾取、碰撞和控制逻辑，使游戏从可观察的初始状态发展为可玩的基础版本。完成基础功能后，你可以选做道具、幽灵行为或地图变化。每项功能都应能在给定的小地图中观察到效果，并能用明确的输入、输出和状态变化检验。

图形界面、地图与资源加载、基本配置和回合循环已由框架提供。每个基础阶段的小节都列出需要完成的接口、GUI 中应看到的效果和对应的公开测试。你可以结合框架代码理解接口，只需修改任务中标明的实现；GUI 和测试会调用同一份代码。

## 运行基础任务

你在 `src/tasks/basic/` 下依次完成 `s1.py`～`s5.py`。每个文件包含两个接口，你可以自行增加辅助函数。为所用的 Python 安装依赖后，在仓库根目录运行当前阶段的 GUI 和测试。例如，完成 S1 时使用：

```bash
python -m pip install -r requirements.txt
python src/main.py --stage S1
python -m tests S1
```

完成后续阶段时，把 GUI 和测试命令中的 `S1` 都换成当前阶段编号；GUI 命令还可用 `--map` 选择文本地图。阶段功能逐步累积，未完成的接口会保持可运行的初始行为，因此窗口可以打开，但目标效果尚不会出现。

```bash
python -m tests framework
python -m tests all
```

`framework` 只检查框架，`all` 运行全部基础阶段测试。`python -m tests S3` 这样的阶段命令会先检查框架，再测试并评分 S1～S3；其他阶段同理。框架检查未通过时，不运行学生测试。每阶段须同时通过该阶段的公开测试和累计游戏检查，才获得该阶段全部分数；其中一项未通过则得 0 分。未完成的阶段测试失败是正常的。

## 共同约定

- 坐标 `(x, y)` 表示列和行：向右时 `x` 增加，向下时 `y` 增加。
- 合法的移动动作是右 `(1, 0)`、下 `(0, 1)`、左 `(-1, 0)`、上 `(0, -1)`；动作 `(0, 0)` 表示**等待**，不是地图左上角的目标坐标。其他动作均无效。
- 墙壁与地图外不可通行。普通豆和能量豆所在的格子可以通行；角色的位置与地图地形分开保存。
- 控制器只选择动作，可以保存自己的策略状态；不得直接移动角色、清除豆子或修改角色分数及生死状态。
- 每个有效回合开始时，已有无敌剩余回合数减少一，最低为 0；之后玩家移动并拾取，再检查碰撞和结果。游戏仍在进行时，活着的幽灵依次行动，每只幽灵行动后再次检查碰撞和结果。
- 拾取能量豆会在**当回合碰撞检查之前**把无敌剩余回合数刷新为配置值。碰撞判定时，剩余回合数 **大于 0** 表示无敌；**等于 0** 表示普通状态。不存在“刚进入无敌状态但剩余 0 回合”的含义。
- 等待或尝试撞墙会消耗一个有效回合。无效的玩家动作应报错，且不推进该回合。玩家死亡优先于清空最后一颗豆子的胜利判定；普通豆和能量豆都清空才算获胜。游戏结束后再次推进不会改变状态。
- 配置中的分数、时长和地图尺寸可能变化；不得依赖固定分值、固定地图或随机胜率取得正确结果。

完成基础函数时，你可以读取 `env.rows`、`env.cols`、`env.get_tile(x, y)`、`env.player`、`env.ghosts` 和 `env.config`。角色提供 `x`、`y`、`live` 和 `env`；玩家另有 `score` 和 `state`（无敌剩余回合数）。需要改变地形时使用 `env.set_tile(x, y, value)`。地形常量 `ROAD`、`WALL`、`POINT`、`POWER` 与方向常量 `DIRECTIONS`、`WAIT` 已在框架中定义。各函数能修改的状态以该题说明为准。

### S1：地图通行与角色移动（14 分）

你需要完成 `src/tasks/basic/s1.py` 中的两个函数：

| 函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `can_walk(env, x, y) -> bool` | 地图与目标坐标；返回能否通行 | 仅当坐标在地图内且目标格不是墙壁时返回 `True`。豆子和空路可通行。地图外返回 `False`，不得因越界读取而抛出 `IndexError`；不修改地图或角色。 |
| `move(agent, direction) -> bool` | 角色与动作；返回位置是否改变 | 存活角色收到四向动作且目标格可通行时，移动**恰好一格**并返回 `True`。等待、撞墙、越界或角色死亡时保持原位并返回 `False`。其他动作抛出 `ValueError`；不得修改地形、分数和角色状态。 |

`direction` 是动作向量。**传入动作 `(0, 0)` 表示等待**，不是目标坐标；等待不需要计算目标格。非法动作即使作用于死亡角色，也应抛出 `ValueError`。移动规则对玩家和幽灵相同。

本题只处理基础位置变化，不负责拾取和碰撞。

- **GUI 效果：**运行 `S1`，在初始地图中按右键，玩家应沿通道移动；走到通道尽头时会被墙壁挡住。经过豆子时豆子仍留在地图上，这是 S2 尚未完成时的预期效果。
- **公开测试：**`tests/test_basic.py` 中的 `test_s1_walkability`、`test_s1_move_and_wait`、`test_s1_invalid_direction` 检查通行、移动与等待、非法动作；`test_integration_s1` 检查游戏中的移动效果。运行 `python -m tests S1`。

### S2：拾取与无敌计时（12 分）

你需要完成 `src/tasks/basic/s2.py` 中的两个函数：

| 函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `advance_power(player) -> None` | 玩家；无返回值 | 每个有效回合开始时，将已有无敌剩余回合数减少一，最低为 0；不改变分数、位置或地图。无效动作不会调用本函数。 |
| `collect_item(player) -> None` | 已成功移动的玩家；无返回值 | 根据玩家**当前格**拾取：普通豆加 `get_point`，能量豆加 `get_power` 并把无敌剩余回合数设为 `power_turns`；两者都把格子变为空路。空路不改变分数或计时。 |

拾取发生在本回合计时减少之后、碰撞检查之前。同一颗豆不能重复得分；多次拾取能量豆刷新完整时长，不累加。幽灵走过豆子不触发拾取，等待或撞墙也不调用 `collect_item`。

### S3：碰撞与胜负（14 分）

你需要完成 `src/tasks/basic/s3.py` 中的两个函数：

| 函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `resolve_collisions(env) -> None` | 当前地图和角色；无返回值 | 只处理存活玩家与存活幽灵同格的情况。玩家 `state > 0` 时使同格活幽灵死亡，并按每只幽灵增加 `beat_ghost` 分；`state == 0` 时使玩家死亡、分数归零。已死亡幽灵不参与；重复调用不得重复计分。 |
| `check_result(game) -> str` | 当前游戏；返回 `running`、`won` 或 `lost` | 玩家死亡返回 `lost`；否则，地图上没有普通豆和能量豆时返回 `won`；其余返回 `running`。本函数只报告结果，不自行移动角色或改动地图、分数和生死状态。 |

如果玩家死亡与清空最后一颗豆子发生在同一回合，结果为 `lost`。没有同格碰撞时，`resolve_collisions` 不改变状态；无敌玩家与多个活幽灵同格时，每只幽灵分别处理。

- **GUI 效果：**运行 `S3`，从起点向右走入固定幽灵，普通状态下应出现失败画面；重开后绕路取得能量豆，再接触幽灵，应看到幽灵消失且分数增加。清空普通豆和能量豆后出现胜利画面。
- **公开测试：**`tests/test_basic.py` 中的 `test_s3_normal_and_powered_collision`、`test_s3_result_and_death_priority` 检查碰撞与胜负；`test_integration_s3` 检查游戏中的普通和无敌碰撞。运行 `python -m tests S3`。

### S4：随机幽灵（8 分）

你需要完成 `src/tasks/basic/s4.py` 中的两个函数：

| 函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `legal_directions(controller) -> list[tuple[int, int]]` | 控制器；返回四向动作列表 | 查看 `controller.agent` 的当前位置，按**右、下、左、上**的顺序列出能进入的相邻格。不得包含等待；完全被困时返回空列表。 |
| `random_direction(controller) -> tuple[int, int]` | 控制器；返回一个动作 | 从当前合法方向中随机选择一个；没有合法方向时返回 `(0, 0)`。返回值必须是四向动作或等待，不得返回墙壁或地图外的方向。 |

这两个函数只作决策，不移动角色，也不修改地图、分数或角色状态。每次调用都依据当前位置重新判断，不能把某张演示地图的结果写死。

- **GUI 效果：**运行 `S4`，按方向键开始游戏后，幽灵应从原地等待变为在通路中移动；在墙边或死路不会穿墙。玩家仍可用键盘移动。
- **公开测试：**`tests/test_basic.py` 中的 `test_s4_legal_directions_and_order`、`test_s4_random_direction_and_trapped` 检查合法方向和随机选择；`test_integration_s4` 检查幽灵在游戏中移动。运行 `python -m tests S4`。

### S5：键盘与转弯缓存（12 分）

你需要完成 `src/tasks/basic/s5.py` 中的两个函数：

| 函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `handle_key(controller, key) -> bool` | 键盘控制器和按键名称；返回是否识别 | 识别 `left`、`right`、`up`、`down` 和 WASD，不区分大小写；空字符串表示等待。识别后把动作存入 `controller.pending` 并返回 `True`。其他字符串返回 `False`，且不改变当前方向或待执行方向。后来的有效按键覆盖旧请求。 |
| `continuous_direction(controller) -> tuple[int, int]` | 连续模式控制器；返回本回合动作 | `pending` 是最近一次接受的动作，初始值 `(0, 0)` 表示等待。它在当前位置可执行时，更新 `controller.direction`；暂时受阻时保留请求，继续返回当前方向，到路口再转向。没有新的按键时保持当前方向；等待请求使当前方向变为 `(0, 0)`。 |

已经执行的转弯不再是待执行请求，`pending` 可以保留为当前方向；只有受阻的新方向需要继续缓存。当前方向即使受阻，也可继续返回，由 S1 阻止穿墙。这两个函数可以更新控制器自己的 `pending` 和 `direction`，但不得直接移动角色或修改地图。终端单步模式已经提供。

- **GUI 效果：**运行 `S5`，先沿走廊移动，在到达路口前按下暂时受阻的方向；玩家应继续前进，并在第一个可转弯格自动转向。提前按下另一方向时，应以较新的请求为准。
- **公开测试：**`tests/test_basic.py` 中的 `test_s5_key_handling`、`test_s5_buffered_turn`、`test_s5_new_request_replaces_old`、`test_s5_wait_and_resume` 检查按键与转弯缓存；`test_integration_s5` 检查游戏中的提前转弯。运行 `python -m tests S5`。

### A 类：道具机制

#### A1：范围冰冻豆（15 分）

| 拟定函数 | 输入与返回值 | 必须满足的行为 |
| --- | --- | --- |
| `advance_freeze(env) -> None` | 当前环境；无返回值 | 每个有效回合开始时，将每只幽灵已有的 `freeze_remaining` 减少一，最低为 0；不改变幽灵位置、分数或生死状态。 |

### B 类：更强的幽灵

| 拟定函数 | 输入与返回值 | 必须满足的行为 |

巡逻路线由一组可达航点构成；幽灵到达当前目标航点后，转向下一个，最后一个之后回到第一个。警戒结束时继续前往中断前的目标航点，前往航点的路径由已有接口提供。你可以在控制器中保存目标航点、警戒状态和未看见玩家的次数，但不能修改地图或角色状态。只选做 B1 时，警戒期间可使用已提供的追逐行为。GUI 会标出幽灵当前状态。

- **GUI 效果：**幽灵先沿路线巡逻；玩家进入无遮挡视野后，状态标识切为警戒并开始追逐；玩家脱离视野足够久后恢复巡逻。
