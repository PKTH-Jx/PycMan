# PycMan 期末大作业设计草案

本文记录面向大一同学的任务设计，供教师准备作业骨架和自动评测时使用。以下 task、启动器和评分测试是待实现的方案，不代表当前仓库已经提供这些入口。任务数量、分值和难度可按课程内容调整。

## 核心原则

每个 task 都是一份可以独立启动、通过 GUI 观察效果的小游戏。学生只补全本题指定的功能，其余功能使用教师提供的完整实现。

- `Game.step()`、GUI、资源加载和基本配置始终由教师提供，不作为挖空内容。
- 不要求先完成前一题；任何 task 都能单独尝试、调试和提交。
- 骨架在未完成时也能打开窗口。目标功能可以暂时缺失，或使用题目明确说明的简单基线。
- 学生修改后，GUI 与测试使用同一份学生实现。运行失败时显示真实错误，不自动替换为教师答案。
- 自动测试按照明确的行为规格评分，不依据人工游戏表现或随机胜率评分。

“能够运行”表示启动入口和演示环境完整，并不表示未完成的功能已经正确。例如移动题的初始角色可以保持静止，碰撞题的初始角色可以重叠；这些都是有意保留的待补全行为。

## 任务总览

| Task | 补全内容 | 初始 GUI 行为 | 完成后可观察的效果 | 建议分值 |
| --- | --- | --- | --- | ---: |
| 1. 合法方向 | `Controller.legal_directions()` | 玩家可键盘控制，随机幽灵原地等待 | 幽灵开始在可通行方向中随机移动 | 8 |
| 2. 角色移动 | `Agent.move()` | 地图、角色和按键响应正常，角色暂时静止 | 玩家与幽灵能够移动，墙壁和边界阻止移动 | 12 |
| 3. 拾取与计分 | 从 `Player.move()` 拆出的拾取方法 | 玩家能够移动，豆子尚不消失 | 普通豆加分，能量豆加分并触发无敌 | 12 |
| 4. 碰撞规则 | `Env.resolve_collisions()` | 玩家和幽灵能够重叠，尚不处理碰撞 | 普通玩家死亡，无敌玩家吃掉幽灵 | 12 |
| 5. 转弯缓存 | `KeyboardController.get_direction()` 的连续模式 | 合法按键可立即转向，暂不缓存受阻的转弯 | 提前按下方向，到路口自动转弯 | 12 |
| 6. 幽灵追逐 | 新增 `ChaseController.get_direction()` | 幽灵使用随机移动基线 | 幽灵沿最短路径追逐玩家 | 14 |
| 7. 自动吃豆 | `BFSController.get_direction()` | 自动玩家使用随机移动基线，无幽灵干扰 | 玩家寻找最近的可达豆子，逐步清空地图 | 16 |
| 8. 无敌时逃跑 | 新增 `FleeController` 的逃跑分支 | 幽灵始终使用教师提供的追逐逻辑 | 玩家无敌时幽灵逃跑，到期后恢复追逐 | 14 |

建议总分为 100 分。Task 6–8 涉及搜索，可以提供 BFS 骨架，或按课程进度设为进阶题。Task 8 的追逐逻辑由教师提供，不依赖学生是否完成 Task 6。

## 各题规格与测试

### Task 1：合法方向

返回能移动到可通行格子的方向列表。只包含四个基本方向，不包含等待；墙壁和地图外的位置不可通行。调用不得移动角色或修改地图。

测试覆盖四个方向、路口、死路、完全被困、开放边界和非正方形地图。若要求列表顺序，公开规定使用框架的 `DIRECTIONS` 顺序。

演示地图包含路口和死路；教师提供的随机 controller 调用本题方法，被困时返回等待。

### Task 2：角色移动

合法方向让存活角色移动一格并返回 `True`。等待、撞墙、越界或死亡角色不移动并返回 `False`；非法方向抛出 `ValueError`。基础移动只处理位置，不处理豆子和碰撞。

测试覆盖坐标变化、返回值、边界、非法方向以及不修改地形。GUI 由教师的玩家拾取逻辑和回合循环调用学生移动方法。

### Task 3：拾取与计分

教师先将拾取逻辑从 `Player.move()` 拆为独立方法，例如 `collect_item()`。基础移动成功后，由教师代码调用学生方法。

- 普通豆：增加配置中的 `get_point`，将该格变为空路。
- 能量豆：增加 `get_power`，将该格变为空路，无敌剩余回合刷新为 `power_turns`。
- 空路：不改变分数和无敌时间。
- 同一颗豆只能拾取一次；不使用写死的分值或时长。

测试直接设置位置和地形，覆盖普通豆、能量豆、空路、重复调用及不同配置。演示地图安排连续普通豆与两颗能量豆，便于观察计分和时长刷新。

### Task 4：碰撞规则

只处理存活玩家与存活幽灵位于同一格的情况。玩家无敌时幽灵死亡，玩家获得 `beat_ghost` 分；普通状态下玩家死亡，分数归零。已死亡幽灵不参与碰撞，重复调用不得重复计分。

测试直接设置角色位置、存活状态和无敌时间，覆盖不重叠、普通碰撞、无敌碰撞、多个幽灵和重复检查。

演示提供短走廊与能量豆，使用教师提供的固定或等待幽灵策略，让两种碰撞容易复现。

### Task 5：转弯缓存

教师提供按键解析和终端单步模式。学生完成 GUI 使用的连续模式：继续沿当前方向请求移动；新的方向可通行时立即采用，否则暂存，到可执行的位置再转向。后续按键覆盖尚未执行的旧转弯请求。

当前方向受阻时仍可返回该方向，由移动方法阻止穿墙；本方法只选择动作，不执行移动。等待指令的行为沿用公开的框架约定。

测试覆盖持续移动、提前转弯、经过路口、覆盖旧指令、等待和状态不被修改。GUI 地图包含两个连续路口。

### Task 6：幽灵追逐

在当前地图上，以玩家当前位置为目标，返回一条最短可通行路径的第一步。每一步移动代价相同，只允许四向移动。目标与起点重合或不可达时返回等待。

忽略无敌状态和其他幽灵占位，本题只评测静态地形上的追逐决策。玩家移动后，controller 需要依据新位置决策。

测试覆盖直线、绕墙、非正方形地图、不可达目标、移动目标和不修改游戏状态。多条最短路径都接受，不要求与教师路径逐格相同。

演示地图让玩家与幽灵隔墙相邻，便于观察幽灵是否真正绕墙追逐。

### Task 7：自动吃豆

将普通豆和能量豆都视为目标；按迷宫最短路距离选择最近的可达目标，返回通往目标的第一步。没有可达豆子时返回等待。

本题不考虑幽灵，GUI 使用无幽灵地图。等距目标和多条最短路径允许任意最优选择，不要求全局清空路线最短。

测试覆盖最近可达目标、隔墙目标、能量豆、不可达豆子、无目标、连续吃豆及不修改游戏状态。集成测试在连通地图上设置足够的回合上限，检查最终能否清空所有豆子。

可以提供独立的 `shortest_path(env, start, goal)` 接口作为子任务：返回方向列表，起终点相同返回 `[]`，不可达返回 `None`。若拆分评分，应分别测试寻路和目标选择。

### Task 8：无敌时逃跑

普通状态使用教师提供的追逐策略；无敌状态从合法下一步中选择到玩家的迷宫最短路距离最大的方向。玩家状态每次调用时读取，不由 controller 修改。

本题使用玩家与幽灵连通的地图，规定不把等待作为逃跑候选；被困时等待。多个最佳方向都接受。距离基于当前地形和玩家当前位置，不预测未来移动，也不把其他幽灵视为墙壁。

测试覆盖分岔、死路、平局、状态切换和无合法方向。演示地图包含能量豆和环路，便于观察追逐与逃跑的切换。

## 独立运行的工程组织

建议使用共享教师框架和按题隔离的学生模块，避免复制八份完整游戏代码：

```text
framework/                   # 完整运行框架、默认规则和 GUI
tasks/
    task01/
        student.py           # 本题函数或子类，以及可运行的初始实现
        run.py               # 将本题实现接入 GUI
        README.md            # 行为规格、运行命令和观察步骤
        test_public.py       # 公开测试
    task02/
        ...
teacher_tests/               # 示意：实际评分环境单独保存
```

未来启动命令可以统一为 `python -m tasks.task01.run`。这只是拟议命令，当前尚未实现。

Task 1–8 只替换本题的函数或类，其余部分使用教师实现。现有 `Game` 和 `GUI` 已支持 controller 工厂；移动、拾取、碰撞题还需要教师补充角色或环境的工厂入口，并将拾取方法拆出。所有任务仍共享教师实现的 `Game.step()`。

教师答案和隐藏评分测试不随学生骨架发放。教师框架可提供非本题功能的完整代码，但本题答案不能通过备用入口暴露给学生。

## 统一运行规则

沿用现有游戏规则，并在学生说明中公开：

1. 合法回合开始时，已有无敌时间减少一，最低为零。
2. 玩家移动和拾取；新能量豆刷新完整无敌时间。
3. 立即检查玩家所在位置的碰撞和游戏结果。
4. 游戏仍在运行时，依次移动每个活着的幽灵，每次移动后检查碰撞和结果。
5. 等待或撞墙也消耗回合。显式非法玩家动作抛异常，不执行该回合。
6. 普通豆和能量豆全部清空才算胜利；死亡优先于胜利。
7. 游戏结束后再次调用 `step()` 不再推进状态或查询 controller。

controller 只读取世界状态、维护自己的策略记忆并返回动作；不得直接调用移动方法、清除豆子、改变位置、分数或角色状态。

## 自动评测原则

- 每题单独测试和计分，不依赖其他 task 的学生代码。
- 用小地图和直接构造状态验证行为；使用不同尺寸、位置和配置排除硬编码。
- controller 测试检查调用前后的地图、位置、分数与状态，确保没有越权修改。
- 随机基线只用于演示。规则测试使用确定性场景；涉及随机性时固定种子或注入固定策略。
- 搜索结果验证合法性和最优性，不绑定教师实现细节。平局接受范围必须在规格中说明。
- 公开测试展示典型输入，隐藏测试覆盖相同规格下的其他输入和边界，不加入未公开规则。
- 搜索和集成测试设置超时与回合上限，并给出可定位到 task 的失败信息。
- 单项行为测试和完整 GUI 启动检查分开。GUI 冒烟测试可以使用 SDL dummy 驱动，不以像素截图作为主要评分依据。

现有 `tests/test_controller.py`、`tests/test_power.py`、`tests/test_maps.py` 可作为教师回归测试基础，但仍需补充按题评分测试及 Task 6–8 的算法测试。

## 实施顺序

1. 保留当前完整游戏作为教师参考实现，确认回归测试通过。
2. 增加功能替换入口与统一 task 启动器，不改变 `Game.step()` 的学生可见职责。
3. 先制作移动、拾取、碰撞三个基础任务，验证每份初始骨架都能启动 GUI。
4. 补充 controller 任务、专用地图、公开测试和隐藏评分测试。
5. 分别验证未完成骨架的演示、正确实现的通过情况，以及典型错误实现是否被测试捕获。
6. 按课程进度确定最终题目、分值和学生发布包。
